# Agentic Text-to-SQL: Tiered LLM Orchestration, Fine-Tuning & Inference Optimization

**Project Type:** Engineering POC with lightweight MLOps/Deployment  
**Objective:** Extend an existing banking-domain Text-to-SQL + RAG pipeline into a tiered, multi-model agentic system. Demonstrate practical expertise in PEFT/QLoRA, AWQ/GPTQ quantization, vLLM inference, adaptive routing, experiment tracking and automated deployment.

**Primary Goal:** Fill LLM infrastructure and production-oriented MLE skill gaps through working implementations and measurable experiments.

## 1. Core Architecture

### A. Tiered LLM Stack & Adaptive Orchestration

Implement a three-tier model architecture:

| Tier | Model | Responsibility |
|---|---|---|
| Master / Orchestrator | Luna (low) | Intent understanding, task planning, model selection, tool orchestration, result synthesis |
| Reasoning | DeepSeek V4.1 Flash | Complex SQL generation, schema reasoning, difficult query correction |
| Local Specialist | Fine-tuned 1.5B–3B LLM | Routine SQL generation and simple error correction |

**Orchestration:**
- Plan–Execute: Decompose requests into retrieval, generation, validation, execution and analysis.
- Adaptive Routing: Route tasks based on complexity.
- Escalation: Escalate failed or low-confidence local predictions to DeepSeek.
- Result Synthesis: Luna generates the final response.
- Cost Tracking: Capture token usage, model selection and estimated cost per query.

Keep routing lightweight using rules and confidence/failure signals.

### B. Hybrid RAG (Reuse nse-rag)

Reuse the existing `nse-rag` retrieval implementation and adapt it for database schema retrieval.

- Dense retrieval using embeddings and Chroma.
- BM25 keyword retrieval.
- Reciprocal Rank Fusion (RRF).
- Cohere Rerank v5 Fast for optional candidate reranking.
- Retrieve relevant tables, columns, descriptions and relationships.
- Inject retrieved schema context into SQL-generation prompts.

Reuse existing retrieval, ranking and metadata-handling components wherever practical rather than rebuilding them.

### C. PEFT / QLoRA Fine-Tuning

- Select a compact code-capable base model (approximately 1.5B–3B parameters).
- Prepare synthetic banking-domain Text-to-SQL examples using the existing database schema.
- Include synthetic SQL error-correction examples.
- Fine-tune using QLoRA with Hugging Face PEFT, bitsandbytes and TRL.
- Save and load the LoRA adapter.
- Compare base-model and fine-tuned-model performance on held-out queries.

**Deliverable:** Reproducible training script, LoRA adapter and evaluation results.

### D. Model Quantization (AWQ / GPTQ)

Explore post-training quantization of the fine-tuned model for efficient inference.

- Generate AWQ and GPTQ quantized model variants.
- Evaluate compatibility with the selected vLLM serving configuration.
- Compare against the original model.
- Measure VRAM consumption, inference latency, throughput and SQL execution accuracy.
- Document quality-versus-efficiency trade-offs.

### E. vLLM Inference Serving

- Deploy the fine-tuned model using vLLM.
- Expose an OpenAI-compatible inference endpoint.
- Integrate the endpoint into the local-model tier.
- Enable automatic prefix caching.
- Benchmark baseline inference against vLLM.
- Evaluate serving performance of quantized variants.

**Metrics:** P50/P95 latency, throughput, tokens/sec and GPU memory utilization.

### F. Agentic Text-to-SQL Pipeline

Preserve the useful components of the original Azraq NLP2SQL project:

1. **Proposal Generator:** Interpret natural-language requests and create execution plans.
2. **Schema Lookup:** Retrieve relevant tables, columns and relationships using hybrid RAG.
3. **SQL Generation:** Generate SQL using the selected model.
4. **SQL Validation:** Syntactic, schema and execution validation using SQLGlot and SQLAlchemy.
5. **Error Corrector:** Localize execution errors and generate corrected SQL using model feedback.
6. **Data Analyzer:** Analyze results using pandas and generate concise insights.
7. **Visualization:** Optional Plotly charts.

### G. Experiment Tracking & Observability

**MLflow**
- Track QLoRA training experiments, hyperparameters and evaluation metrics.
- Compare base and fine-tuned model runs.
- Track quantization experiments and model artifacts.

**Langfuse**
- Trace LLM calls and agent execution.
- Monitor model routing, token usage and latency.
- Inspect generation, retrieval and correction traces.

### H. CI/CD & Automated Deployment

Implement a lightweight deployment workflow:

- Dockerize the application and inference services.
- Use Docker Compose for local orchestration.
- GitHub Actions for automated tests and Docker image builds.
- Automate deployment to a single cloud or GPU-enabled host.
- Maintain a simple configuration-driven deployment process.

No Kubernetes or distributed infrastructure.

### I. Demo Application

Build a lightweight Streamlit interface displaying:
- Natural-language query input.
- Selected model and routing decision.
- Generated SQL and validation status.
- Execution results and correction attempts.
- Data analysis and optional visualizations.
- Basic latency and token/cost information.

## 2. Evaluation & Benchmarking

Create approximately 100–200 banking-domain evaluation queries using the existing database schema and synthetic data.

| Experiment | Comparison |
|---|---|
| Fine-tuning | Base LLM vs. QLoRA |
| Quantization | Original vs. AWQ vs. GPTQ |
| Inference | Baseline vs. vLLM |
| Prefix caching | Disabled vs. enabled |
| Orchestration | Single-model vs. tiered routing |

**Metrics:**
- SQL execution accuracy and first-pass validity.
- SQL repair success rate and average retries.
- End-to-end latency (P50/P95).
- Inference throughput and tokens/sec.
- GPU memory utilization.
- Estimated cost per successful query.
- Quantization-induced accuracy degradation.

Use a held-out evaluation set and consistent test conditions.

## 5. Development Constraints

- Engineering POC, not a full production application.
- Reuse existing Text-to-SQL and nse-rag code wherever possible.
- Local development on RTX 3060 Ti (8GB VRAM); rent cloud GPU compute when necessary.
- Keep orchestration, routing and error handling simple.
- No Kubernetes, distributed serving, multi-LoRA or extensive security hardening.
- Prefer existing libraries and implementations over custom infrastructure.
- Prioritize working implementations and measurable results over feature completeness.
